## 2. Navigation
Bottom bar: Home, Watching (Hall Monitor, Activity), Library (Smart lists, Libraries, **Hall Pass**, a debug-only Tags placeholder), Server (Live, Tasks, Activity, Devices, Plugins), Settings. Profile (Parent / Administrator / Custom) is per phone and decides the tabs and Home cards. GroupTabs uses a HorizontalPager (so horizontal gestures inside a tab can fight the pager: the swipe review is a full-screen Dialog for that reason).

## 3. Hall Pass tab (Library > Hall Pass)
Files: `data/HallPass.kt` (models, tolerant parser, version gate `HallPass.MIN_PLUGIN = "1.2.0.0"`), `ApiClient.hp*` (calls `/emby/HallPass/...` with the signed-in **administrator's token**, no separate key), `hallpass/HallPassViewModel.kt`, `HallPassScreen.kt`, `HallPassSwipe.kt`. Features: summary card (counts, scan progress, Scan now / Scan all again / Apply...), "What to do next" card (`nextStep`, five steps, says where the dry-run switch is: plugin page Settings > Tags & writing), filters (Needs review, Explicit, Likely clean, Clean, All; reason chips with counts when Needs review), Tracks / Albums / Artists, Order A to Z / Most played, search, track cards (Explicit / Clean / Clear, tap for evidence, plays), album and artist cards (Open, All explicit, All clean with a confirmation), "Decide faster" card (swipe review; All N explicit / All N clean for the current view with a confirmation that spells the view out: `describeView`), apply preview dialog (only offers to write when dry run is off). Swipe review: right = clean, left = explicit, threshold 30% of the width (`swipeOutcome`), Skip moves a track to the end, Undo clears the manual decision; decisions leave the list at once and go to the plugin in the background, a failure restores the track (`decidedInSwipe` filters stale reloads). Settings (word list, online lookups, roll-up, dry run) deliberately stay on the plugin's Emby page: they change what is sent out or written.

## 4. Hall Monitor additions (needs plugin 2.1.0.0, `ApiLevel >= 3`)
`UserStatus` reads `WatchedToday/Week/Month/YearSeconds` and `WatchedTrackingSince` (kept, not shown). The Home "Kids today" card shows watched today and week, then month and year (`WatchText.total`); the Hall Monitor card shows the same line. The footnote about when counting started was removed at the owner's request. With an older plugin the card keeps its old "This week" line. The three-dot item reads "Reset today's time..." with a "Fresh day" dialog on plugin 2.1 (Reset now only zeroes today's allowance and extra time). Background: weekly reset was off for the owner's children, Reset used to zero day, week, month and year together (that made one child's week look wrong and another's zero), and the owner wants totals of time really watched that no reset touches (a permanent ledger in the plugin, `docs`/PROGRESS section 16 of the plugin repo).

## 5. Decisions worth knowing (more in decisions.md)
- No app lock and no FLAG_SECURE (decided twice). HTTPS only, no redirects, token only in `X-Emby-Token`, ids validated through `seg`.
- Hall Pass tab uses the administrator token; minimum plugin 1.2.0.0 (raised from 1.1.0.0 at 0.8.0 because Artists and plays need it; older plugins get a "too old" card, the rest of the app is unaffected).
- Bulk actions always show the count and the view in the confirmation; nothing is written to files by marking (only Apply writes, and only with dry run off).
- Secrets (Tracearr key, plugin switches) are entered only by the owner.

## 8. Notifications (rebuilt for 0.10.0, 2026-10-14): how it works
Full description: `docs/notifications-plan.md`. The contract for plugins: `docs/push-contract.md`. Decisions and reasons: `docs/decisions.md` ("2026-10-14: notification revamp", "plugin pushes reach the app only through a subscription", the 0.9.1 baseline entry).
- **What the owner sees:** Settings > Notifications: this phone's permission, Pause all, Quiet hours, then one row per service; each service screen has its switch, Sound and vibration (Android's channel screen), Send a test, and every alert type with its rules (switch, edit, delete, add another). Hall Monitor is for every account; Label Maker, Plugin manager, Hall Pass, Smart lists, Tracearr and Emby server only for an administrator account on the Administrator setup (or Custom with Smart Lists on): `NotifAvailability` = `Profiles.showsAdminCards`. A regular account sees only Hall Monitor and a one-line explanation (checked on the emulator).
- **Code map:** `notifications/` (`NotifModel`, `NotifCatalog`, `NotifRules`, `HallMonitorEngine`, `PluginEventEngine`, `NotifHub`, `NotifPoster`), `watching/AlertService.kt` (foreground service that holds the connections while any rule is on), `watching/BackupPollJob.kt` (15-minute JobScheduler failsafe, only while the service is not running; needs `ACCESS_NETWORK_STATE`: its absence crashed the app the first time a service was switched on), `ui/NotificationsScreen.kt`, `push/EmbyPush.kt` + `PushProtocol.kt` (plugin subscription topics).
- **Delivery:** Hall Monitor over its own live subscription (key in the message); Label Maker, Hall Pass, Smart lists and the GitHub plugin manager over an **events subscription each plugin offers** (`<Plugin>EventsStart` with `0,30000,<afterSeq or empty>,<access token>`, answered by `<Plugin>Events`); Emby's task list topic; Tracearr's event stream. After a gap `GET .../Events?After=` catches up; `Seq` dedupes. **Why a subscription:** Emby's `SendMessageToAdminSessions` reaches only websockets that carry the token in the ADDRESS (`?api_key=`), and the app keeps its token in the header; `connection.User` is also empty for a header socket, so the subscription takes the token in the start message body and validates it itself.
- **Alert texts (the owner asked for useful ones, 2026-10-14):** percent alert "Used 1 h 36 min of 2 h allowed today. 24 min left." (allowed includes extra time); used all: "Used all 2 h allowed today. Playback was stopped. Add 30 minutes to let them keep watching."; extra time: "30 min added. Alex now has 1 h left today."; daily summary one line per child. The "used all" alert and Home's "reached their limit" row have ONE button, **+30 min**. The Hall Monitor card has **+30 min** and **-30 min** (takes 30, or everything that is left when less than 30 remain, never below zero; needs Hall Monitor 2.3 / ApiLevel 5 to go below the limit, with older plugins it only takes back extra time and says so).
- **Verified (emulator, throw-away users, real server):** Hall Pass scan alert through the subscription (baseline with empty afterSeq, no replay); plugin-manager run alerts; Hall Monitor 50% alert and used-all alert with exactly one +30 button, the Home +30 row, +30 and -30 on the card, -30 with 3 minutes left taking exactly 3 minutes (allowance 0, status blocked, not negative); Send a test; the regular-account view; plugin side live tests by their sessions (Hall Pass 42 checks, Smart lists 18, GitHub plugin).
- **NOT verified:** a real phone, the lock screen, quiet hours on a device (unit tested), the backup job actually firing (scheduled, not waited for), Label Maker (the plugin has no subscription yet: its session must add `LabelMakerEventsStart`/`LabelMakerEvents`; until then only catch-up and the backup poll can deliver), Tracearr alerts against a real Tracearr, the "Smart lists timer stopped" alert, a weekly or monthly limit firing live.

## 9. How this owner wants work done (essentials; the full list is in `C:\dev\label-maker-emby\docs\HANDOFF.md` section 8)
- Plain-language answers, lead with the result; American English; full sentences in UI copy; no sentence ending in "is" or "are"; say where a setting lives. When one line of copy is criticised, review all copy on that page.
- **Verify, do not guess:** reproduce with real data, look at screenshots, report what was NOT verified. Ask before behavior changes; when the owner says they have no ideas, give options with a recommendation.
- **Release only when the owner says "publish it"** (they said it for 0.9.0, 0.9.1 and plugin 2.2.0.0). Flow: notes `docs/releases/vX.Y.Z.md` committed first and pushed; CI and all CodeQL jobs (the `test` job, `Analyze (java-kotlin)`, `Analyze (actions)`) green on THAT exact commit (poll `https://api.github.com/repos/feerlessleadr/embidextrous/commits/<sha>/check-runs` with `Invoke-RestMethod`; there is no `gh`; 60 requests per hour, so poll about every 75 seconds); `git tag -a vX.Y.Z` on that commit and push the tag; the Release workflow (environment `release`, signing secrets are the owner's) builds and attaches the APK; read size and `digest` from `.../releases/tags/vX.Y.Z`; add the row to the table in section 1 and push. Release a plugin first when the app depends on its new version.
- Ordinary commits may be pushed (standing permission). Commit author `feerlessleadr <github@thecgkg.com>`; the message ends with the attribution line in CLAUDE.md; use `git commit -F <file>`. NEVER put the owner's LAN IP, share names, Windows user name or work email in a tracked file (this public repo's `CLAUDE.md` once held the Windows user name in a path; it now uses `%USERPROFILE%`, but old commits still contain it; rewriting this public history is the owner's call).
- Secrets: never print or store keys, tokens, passwords. The test server's admin key is read from `%USERPROFILE%\.emby-spike-key` by scripts and never printed. Throw-away users and keys only, deleted afterwards.
- **Never leave the test server changed:** restore settings, delete throw-away users, restore any plugin DLL you swapped (byte-identical, compare hashes), stop the server if you started it. Never touch the real test users `kevin` and `test1`.
- Tool traps: PowerShell 5.1 (no `&&`, no `-AsHashtable`, `$PSScriptRoot` is empty in param defaults); a path guard blocks the PowerShell delete cmdlet when the command text contains certain paths or even the cmdlet's name in text, so delete with `[System.IO.File]::Delete` or `[System.IO.Directory]::Delete`, and write long text to files with the Write tool; do not mix PowerShell syntax into Bash tool commands; Gradle needs `JAVA_HOME` = Android Studio's JBR and works with `--offline`.

## 10. Recipes learned on 2026-10-14
- **Emulator typing:** `adb shell input text` drops or repeats characters when fast. Send one character at a time with about 220 ms between (`foreach ($ch in $text.ToCharArray())`), screenshot to check the field, and fix with `keyevent 122` (Home), `keyevent 22` (Right), `keyevent 67` (Delete). Gboard may open a clipboard panel if a tap lands on the keyboard: press Back, relaunch the app. Press Back once to hide the keyboard before tapping buttons. Dark theme: `adb shell cmd uimode night yes` (and `no`). Read stored settings: `adb shell "run-as com.feerlessleadr.embidextrous.debug cat shared_prefs/settings.xml"`. Read posted notifications: `adb shell "dumpsys notification --noredact"`; open the shade: `adb shell cmd statusbar expand-notifications`. Grant the notification permission without a dialog: `adb shell pm grant <pkg> android.permission.POST_NOTIFICATIONS`.
- **End-to-end check of Hall Monitor alerts with real counted playback:** (1) back up the plugin DLL and `programdata\plugins\configurations\HallMonitor.xml` to a temp folder; (2) with the server stopped, copy the plugin build over `programdata\plugins\HallMonitor.dll` and start `system\EmbyServer.exe -programdata <dir>\programdata -ffmpeg <dir>\system\ffmpeg.exe -ffprobe <dir>\system\ffprobe.exe -restartexitcode 3`; wait until `GET /Users` works (the ping answers before the server is ready); (3) create a throw-away child user and a throw-away admin, passwords kept only in temp files; (4) set the plugin config through `POST /Plugins/e8c3b1b3-4f56-4f38-a28a-2e6c5a043007/Configuration` (GET it first, change it, post it back): `EnableWatchTimeLimiter=true`, `EnablePublicApi=true`, `ApiKey=<throw-away, 40 characters>`, `LimitedUsers=[{UserId, Username, IsEnabled=true, EnableDailyLimit=true, DailyLimitMinutes=2, EnableWeeklyLimit=true, WeeklyLimitHours=1, ...}]`; (5) in the app on the emulator sign in as the admin, enter the throw-away key in Settings (Hall Monitor card), add a percent rule; (6) simulate playback as the child: `POST /Users/AuthenticateByName` with the header `X-Emby-Authorization: MediaBrowser Client="LMTest", Device="LMTest", DeviceId="lm-test-1", Version="1.0"`, get an audio item with `Fields=MediaSources`, then `POST /Sessions/Playing` with `ItemId`, the real `MediaSourceId`, a `PlaySessionId` and `PlayMethod=DirectPlay`, then `POST /Sessions/Playing/Progress` every 5 seconds with growing `PositionTicks`; the plugin counts in 15 second ticks, so a 2 minute limit reaches 100% in about 2 minutes; (7) read `GET /HallMonitor/LimitedUsersStatus` (admin token) or `GET /HallMonitor/Public/Status` (headers `X-Emby-Token` and `X-HallMonitor-Api-Key`) and the phone's notification list; (8) clean up: `POST /HallMonitor/DeleteUserData` for the child, delete both users, restore config and DLL from the backups, delete the AVD folder and its `.ini`, delete temp files, stop the server.
- **Plugin regression suite** (`C:\dev\watching-eye\tools\Run-RegressionTests.ps1`): its lockout check locks the public API key for 5 minutes, so a second run straight afterwards fails every key check; restart Emby or use `-SkipLockout`. One push-count check ("five subscriptions produce one push") failed once in four runs and passed otherwise (timing).

- **Plugin push recipes (2026-10-14):** to see what the app would receive, open a `System.Net.WebSockets.ClientWebSocket` with the token in the `X-Emby-Token` header and `deviceId` in the address (NO `api_key`), then send `{"MessageType":"<Plugin>EventsStart","Data":"0,30000,,<token>"}`. Never use a cancelling receive (a cancelled `ReceiveAsync` aborts the socket): wait on the task with a timeout instead. A socket with `?api_key=` behaves differently and proves nothing about the app. Changing a user's password in Emby ends that user's sessions (the emulator signs out): set the throw-away password once per session. Anything in the scratchpad whose name looks like a password file may be deleted by other tools: generate the password and type it in the same command. The shared test server is also used by the other sessions' live test scripts: check for running `Test-*.ps1` first and take turns.
- **Hall Monitor check with real counted playback (used for 2.3.0.0):** back up `HallMonitor.dll` and `configurations\HallMonitor*` first; with the server stopped copy the new DLL and start it (recipe above); create a throw-away child, set the plugin config (`EnableWatchTimeLimiter`, `EnablePublicApi`, a 40 character `ApiKey`, one `LimitedUsers` entry with a 3 minute daily limit); type the key into the app's Settings; switch Hall Monitor alerts on and a 50% rule; play with `play.ps1`-style `Sessions/Playing` plus `Progress` every 5 seconds as the child; read `dumpsys notification --noredact`; use the card buttons; afterwards run `tools\Run-RegressionTests.ps1 -SkipLockout`, restore the DLL and configuration files by hash, delete the child.
